---

## 1. 배경 (왜 Phase 36인가)

Phase 35 마무리에서 두 가지 사실이 실증됨:

1. **안전망(방어)은 동작한다**: T4 발행 경로 실배선 + frontmatter 메타 방어로 dry-run 본문/메타 릭 0건 달성.
2. **그러나 발행할 초안이 없다**: 발행 후보 10006/10007 모두 파손 초안(본문 대부분이 계획텍스트). 생성 파이프라인이 고장 상태로, **정상 초안이 나와야 발행 대상 확보가 가능**.

따라서 Phase 36은 **"생성 복구"(BUG-001/002/003)를 선행하고, 안전망 잔여 구멍(BUG-005/006)을 차단**하는 단계.

## 2. Phase 36 목표

- **정상 초안 생성 파이프라인 복구**: BUG-001(truncation), BUG-002(fallback 파싱), BUG-003(use_context 스킵) 해결로 파손 초안 재발 방지.
- **안전망 잔여 구멍 차단**: BUG-006(파손 초안 발행 게이트), BUG-005(protected 계획텍스트 정밀 스캔)로 오염 발행물이 게이트를 통과하지 못하도록 보강.
- **최종 목표**: 정상 초안 1건 이상 확보 → 기존 dry-run 게이트(T4+FM 메타+D8) 통과 → 대표 승인 후 실발행.

## 3. 우선순위 (근거 포함)

| 순위 | BUG | 근거 |
|------|-----|------|
| (1) | **BUG-001** — truncation | 생성 실패의 최상위 원인. reasoning_content 추출로 응답 절단 → JSON 파싱 실패 → 파손 초안. 해결돼야 정상 초안 자체가 가능 |
| (2) | **BUG-002** — fallback 파싱 | BUG-001의 잘린 응답이 fallback 파싱에서 구조 오인 → 크래시/orphan chain. BUG-001 수정과 병행되어야 파이프라인 안정화 |
| (3) | **BUG-006** — 파손 초안 게이트 | 안전망. 정상 초안 생성 복구 이전에도 파손 초안 발행을 선차단해야 함 (생성 복구 실패 시의 안전판) |
| (4) | **BUG-005** — protected 정밀 스캔 | 안전망. 게이트 통과 후에도 protected 계획텍스트 잔존 위험 차단 (10007 라인 42/47/54 사례) |
| (5) | **BUG-003** — use_context 스킵 | 품질 향상. 컨텍스트 없는 초안이 파손 원인의 일부(추정)지만, truncation 대비 발현 빈도 낮고 영향 상대적 |

**정당화**: 정상 초안이 나와야 발행 대상 확보 가능 → **생성 복구(BUG-001/002)가 안전망 잔여(BUG-005/006)보다 선행**. BUG-003은 발현 빈도(16회 중 12회)가 높으나 근본 원인(truncation)과 독립적 개선으로 후순위 배치.

## 4. 제약 사항

- **발행/배포/push 금지** (게이트 통과 + 대표 최종 승인 전까지).
- **DB 쓰기 금지** (검증은 dry-run/단위 테스트/실DB 격리 patch로만).
- **git checkout/stash/reset 금지**.
- BUG-001/002/003/005/006 수정은 **대표 승인 후** (본 문서 + PLAN.md 승인으로 착수).
- 기존 기능 보존: 수정은 additive, 기존 테스트 green 유지.
